# Arc Monitor

**Исследовательский MVP для Circle Arc: сбор данных → признаки и исходы → локальная веб-панель.**

Это работающий Python-проект, а не только макет интерфейса. Он не подписывает транзакции,
не подключает кошелёк и не отправляет торговые поручения. Демо полностью синтетическое.
Прогнозная ценность оценок и возможность заработать на них **не доказаны**.

## Запуск на Windows

Нужен Python **3.11 или новее**. Распакуйте проект и откройте PowerShell в папке с этим README:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m arc_monitor --db data/demo.db --mode demo demo --serve
```

Откройте **http://127.0.0.1:8000**. Остановка — `Ctrl+C`.
Активация виртуального окружения и изменение ExecutionPolicy не нужны.

Альтернатива — `scripts/run_demo.ps1`: создаёт окружение, устанавливает зависимости и запускает демо.
Когда PowerShell блокирует этот файл, используйте три команды выше, не меняя системную политику.

В демо 7 сценариев: рост покупателей, циклический оборот, прекращение торгов,
снятие ликвидности, общий funder, слишком молодой токен, неизвестное происхождение.
Повторная загрузка демо не дублирует события. Время демосреза фиксировано:
`2026-09-22T12:00:00Z`; оно не движется вместе с часами компьютера.

На Linux/macOS:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
.venv/bin/python -m arc_monitor --db data/demo.db --mode demo demo --serve
```

Установка зависимостей требует интернета. После установки демо, аналитика и интерфейс
работают без внешних запросов; шрифты, графики и JavaScript не используют CDN.

## Что реализовано

| Область | Реализация v0.1 |
|---|---|
| Данные | Валидируемые события, точные Decimal-строки, UTC, атомарная запись, дедупликация, явные конфликты |
| База | SQLite по умолчанию; SQLAlchemy-путь для PostgreSQL с отдельным драйвером |
| Bitquery | HTTP backfill и polling, raw-ответы, повторы 429/5xx, лимит запросов, дробление переполненных интервалов |
| Запуски | Реестр 8 контрактов: Argus, две разновидности RadarDEX, Tolly, Warp, Archemist, PEGD, Minara |
| Ранние события | Чтение indexed topics без зависимости от наличия декодированного имени события |
| Generic discovery | Токен из первой наблюдаемой USDC-сделки; это **не** доказательство времени создания контракта |
| RPC | Проверка chain ID, read-only методы, запуск по логам, ERC-20 interface probe, сравнение двух представлений USDC |
| Ликвидность | Нормализованные исторические срезы; отдельный opt-in запрос текущего пула GeckoTerminal |
| Аналитика | Покупатели, 5-минутная скорость, funding-proxy, повторные круговые сделки, raw/adjusted volume, net flow, ликвидность, держатели |
| Риски | Раздельные Runner/Risk, отсутствие итогового Risk при нехватке основных свидетельств |
| Исследование | Признаки через 5/15/30/60 минут, survival 1/6/24/72 часа, будущие ценовые кратности, цензурирование |
| Интерфейс | Локальная read-only панель, фильтры, сортировка, детали, графики, ограничения качества |
| Уведомления | Локальный журнал и Telegram-адаптер; отправка закрыта до независимой проверки исследования |

Добавлены штатный `.env`, темп и бюджет запросов, учёт пробелов/свежести,
ограниченное обогащение holders/funding/liquidity/контрактных сведений, CCTP-реконсиляция,
временной hold-out и Windows-автозапуск. Практический порядок работы:
[docs/OPERATIONS.md](docs/OPERATIONS.md).

Полные исторические holders, аудит безопасности, доказанная исполнимость сделок,
полный creator P&L, WebSocket, DEXScreener и обученная прогнозная модель не заявляются.
Текущие срезы не заменяют прошлые; неизвестные риски остаются `null`.

## Реальные данные Bitquery

Проверка с ключом 22 сентября: trades/events отвечают, два свежих интервала сохранены,
три сделки сверены с официальным RPC. Обнаружено округление amounts уже в ответе
Bitquery: хранение в Decimal не возвращает утраченную точность.
Полный отчёт и ограничения: [docs/LIVE_INTEGRATION.md](docs/LIVE_INTEGRATION.md).
Сбор ограничивается квотой; актуальное состояние показывает команда `status`.

Ключ хранится локально в `.env` и автоматически читается CLI/ASGI. Переменные процесса
имеют приоритет перед файлом, явные CLI-флаги — перед настройками окружения.
`--env-file PATH` выбирает файл, `--no-env-file` отключает его. Ключ не выводится в журнал.

```powershell
.\.venv\Scripts\python.exe -m arc_monitor doctor

# Сначала небольшая контрольная выборка. Все границы в UTC; end не включается.
.\.venv\Scripts\python.exe -m arc_monitor --db data/arc.db backfill `
  --start 2026-09-16T00:00:00Z --end 2026-09-16T01:00:00Z --max-requests 100

# Затем диапазон из задания, если источник действительно предоставляет эту историю.
.\.venv\Scripts\python.exe -m arc_monitor --db data/arc.db backfill `
  --start 2026-09-16T00:00:00Z --end 2026-09-23T00:00:00Z --max-requests 500
```

**Не запрашивайте будущее:** второй пример охватывает 16–22 сентября целиком и подходит
только после наступления `2026-09-23T00:00:00Z`. При запуске 22 сентября задайте уже
прошедший `--end`, например на две минуты раньше текущего UTC. Иначе ответы за будущее
не могут подтверждать полноту будущей истории. Collector отклоняет будущий end. Перед первым запуском проверьте даты
в Bitquery IDE; наличие API не гарантирует нужную историческую глубину на вашем тарифе.

Полный диапазон может потребовать больше 500 запросов. Лимит относится к **HTTP-запросам
за весь запуск**, включая повторы; это не лимит суммы счёта/кредитов поставщика.
При исчерпании повторите ту же команду: завершённые интервалы будут пропущены.
Если в одной секунде достигнут `--limit`, сбор остановится без ложной отметки о полноте.
Можно увеличить `--limit` до поддерживаемого источником значения, максимум 10 000.
Если этого недостаточно, нужны дополнительные раздельные запросы по рынкам — они пока не реализованы.

Получить точный текст запроса **без ключа и без сети**:

```powershell
.\.venv\Scripts\python.exe -m arc_monitor query --stream launches `
  --start 2026-09-16T00:00:00Z --end 2026-09-16T01:00:00Z > launches.graphql
```

При GraphQL-ошибке программа не превращает её в «ноль сделок». Окно остаётся неподтверждённым.
Текст ошибки поставщика намеренно не выводится целиком, чтобы не раскрывать секреты.
Проверяйте запрос через IDE и сверяйте контракт/tx/pool с независимым источником.

### Polling и интерфейс — два процесса

В первом PowerShell:

```powershell
.\.venv\Scripts\python.exe -m arc_monitor --db data/arc.db poll `
  --interval 60 --lookback-minutes 10 --lag-seconds 120 --max-requests 500
```

Во втором:

```powershell
.\.venv\Scripts\python.exe -m arc_monitor --db data/arc.db serve
```

Polling останавливается по `Ctrl+C`, при исчерпании бюджета или невосстановимой ошибке.
Успешные окна остаются в базе. Есть короткое перекрытие для поздно появившихся событий.
Сначала сохраняются свежие окна, затем по одному старому пропуску каждого потока
за цикл. Остальная история доступна через `backfill`; `--refresh` повторяет уже
покрытые интервалы. Второй управляемый collector для той же SQLite-базы отклоняется.

Панель пересчитывается с 10-секундным кэшем; live-браузер обновляется каждые 30 секунд.
По умолчанию сканируются 500 последних обнаруженных токенов, а не вся возможная сеть;
усечение явно возвращается в API и отображается в интерфейсе. `serve --max-tokens N`
меняет этот предел. Масштабирование на сотни тысяч токенов не проверено.

## Исследование и локальные алерты

```powershell
# Демо-исследование — проверка механики, не доказательство торговой гипотезы.
.\.venv\Scripts\python.exe -m arc_monitor --db data/demo.db --mode demo research --out reports/demo

# Реальная база: cutoff должен соответствовать известной истории.
.\.venv\Scripts\python.exe -m arc_monitor --db data/arc.db research `
  --as-of 2026-09-22T12:00:00Z --out reports/live

# Только локальное сохранение кандидатов; ничего не отправляется наружу.
.\.venv\Scripts\python.exe -m arc_monitor --db data/arc.db alerts --min-runner 65 --min-risk 60
```

Результаты: `features_and_outcomes.csv` и `summary.json`. CSV безопасно экранирует
формулы в недоверенных символах токенов. Исторические признаки используют события
**строго до** feature cutoff. Будущие цены используются только для label.
Незрелый горизонт и неполная история дают `null`, а не отрицательный исход.
Пустой будущий поток подходящих сделок не становится доказанным x0.

Survival — заранее заданное наблюдаемое условие, не обещание ликвидности:
на 1 часе ≥2 funding-proxy участников в минутах 45–60; на 6/24/72 часах —
в последнем часе. Для 6 часов дополнительно нужна свежая ликвидность ≥1000 USDC.
Сделки creator и выявленные круговые сделки исключаются; минимальный размер для
survival — 1 USDC. Это формальные правила MVP, которые ещё надо проверить на реальном рынке.

Baseline появляется после 10 funding-proxy покупателей с покупками ≥10 USDC.
Для прогнозных ценовых labels reference — последняя подходящая сделка **перед**
feature cutoff, а максимум — только после него. Не смешиваются рост до сигнала и после сигнала.
Это **ценовые кратности**, не историческая доходность исполнимой стратегии:
нет проскальзывания, комиссий, налогов токена, MEV, ограничений продажи и задержек API.
В `purged_time_split` обучающие label-окна отделены от времён test-признаков;
команда `evaluate` выполняет purged hold-out и сравнение фиксированных правил.
Отчёт текущей live-базы: `insufficient_data`; полезность признаков не подтверждена.
Условные сценарии комиссий/проскальзывания вынесены отдельно от ценовых labels.
Подробности: [docs/EVALUATION.md](docs/EVALUATION.md).

## Дополнительные входы

```powershell
# Сначала настройте доверенный RPC; endpoint автоматически проверяется на chain ID 5042.
$env:ARC_RPC_URL = Read-Host 'Trusted Arc mainnet RPC URL'
.\.venv\Scripts\python.exe -m arc_monitor rpc-check
.\.venv\Scripts\python.exe -m arc_monitor --db data/arc.db rpc-launches --start-block 1 --end-block 500

# Нормализованный импорт. Ничего не записывается, если хотя бы одна строка некорректна.
.\.venv\Scripts\python.exe -m arc_monitor --db data/arc.db import-jsonl events.jsonl
```

Схемы находятся в `src/arc_monitor/models.py`, примеры — в `examples/`.
Значения сумм передавайте decimal-строками в human units, не raw uint256 и не float.
Функция `units(raw, decimals)` преобразует исходные единицы отдельно.
Максимальная величина поля — `1e78`, максимум 36 знаков после запятой.

Обычный JSONL не подтверждает историческое покрытие. `Store.record_window(...)`
предназначен для адаптера, который действительно проверил окно; нельзя добавлять
покрытие лишь для получения ненулевого survival отчёта.

Текущий срез GeckoTerminal для **известного** пула:

```powershell
.\.venv\Scripts\python.exe -m arc_monitor --db data/arc.db liquidity --token $TokenAddress --pool $PoolId
```

`$TokenAddress` и `$PoolId` — реально проверенные адрес и идентификатор пула,
не тикер и не общий Uniswap v4 PoolManager. USD reserve помечается
`usd_assuming_usdc_peg`; его нельзя выдавать за точный баланс USDC или прошлый срез.
Запрос выполняется только явно, не чаще разрешённого лимита поставщика.

## Как устроены оценки

Runner v1: новые funding-proxy группы (до 30), число групп покупателей (до 20),
логарифм adjusted volume (до 20), положительный net flow (до 15), liquidity retention (до 15).
При отсутствии funding-наблюдений кошельки остаются отдельными, но funding coverage
виден рядом. Это не доказательство их независимости.

Risk v1: наблюдаемые wash-признаки, concentration, общий funder (эвристический штраф до 35), налоги, опасные разрешения,
состояние LP и падение ликвидности. Итоговый Risk отсутствует без проверки
контракта, полного holders-среза, свежей ликвидности и недавних торгов.
Внутренняя оценка по известным полям не выдаётся за полный рейтинг безопасности.
Формулы открыты в `metrics.py`, версия — `heuristic-v1-unvalidated`.

Adjusted volume исключает сделки, попавшие под ограниченный набор round-trip эвристик;
арбитраж тоже может попасть под фильтр, а сложный wash — пройти через него.
Нулевой net flow сам по себе не доказывает wash. Из holder concentration исключаются
пулы/локеры/протокольные и burn-адреса **только при наличии соответствующей разметки**.
Сам creator автоматически из распределения не удаляется.

и нагрузочные характеристики PostgreSQL требуют отдельной проверки.

## Загрузка в ваш GitHub

Из этой сессии запись в `kuilef/arc_monitor` была отклонена:
`403 Resource not accessible by integration`. Наличие готового архива **не означает**,
что файлы уже находятся в удалённом репозитории.

Через установленный у вас Git и вашу локальную авторизацию:

```powershell
# Из распакованной папки проекта. Сначала создаётся только локальный коммит:
.\.venv\Scripts\python.exe scripts/publish.py

# Затем явная отправка HEAD в main (без force push):
.\.venv\Scripts\python.exe scripts/publish.py --push
```

Git должен знать ваши `user.name`/`user.email`, а локальная авторизация — разрешать
запись в репозиторий. Ключ или GitHub-токен в чат передавать не требуется.
При появлении чужих/новых коммитов удалённая история не переписывается: обычный push
будет отклонён и потребует согласования истории.

Приложен также Git bundle для переноса уже созданной истории:

```powershell
git clone arc_monitor.bundle arc_monitor
```

После клонирования bundle установите origin на свой GitHub-репозиторий:

```powershell
cd arc_monitor
git remote set-url origin https://github.com/kuilef/arc_monitor.git
git push -u origin HEAD:main
```

## Безопасность и эксплуатационные ограничения

Приложение предназначено для одного пользователя и локального запуска. HTTP API не
имеет аутентификации и намеренно не имеет mutation-endpoints. Не публикуйте порт в
интернет; для удалённого доступа используйте доверенный туннель. CORS не открывается,
Host проверяется, недоверенные названия выводятся через `textContent`, действует CSP.

Перед обновлением остановите collector и dashboard. SQLite-база должна оставаться в
`data/`; для резервной копии остановите процессы или используйте SQLite backup API,
а не копирование одного `.db` посреди активной WAL-записи. Windows-автозапуск:
`scripts/install_autostart.ps1`; архивная ротация данных не реализована.
Потерянные незавершённые окна запрашиваются повторно, локальные бюджеты сохраняются.
