# Ежедневная работа

Все команды запускаются из корня проекта. `.env` уже содержит локальный ключ;
CLI читает файл сам. Значения процесса имеют приоритет над `.env`, CLI-флаги —
над окружением. Файл не исполняется, не подставляет переменные и не попадает в Git.

```powershell
# Запуск сбора с сохранением журнала; Ctrl+C завершает текущий процесс.
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run_monitor.ps1

# Панель в другом окне.
.\.venv\Scripts\python.exe -m arc_monitor serve

# Покрытие, свежесть и причина остановки, без запросов к поставщику.
.\.venv\Scripts\python.exe -m arc_monitor status
```

Панель: http://127.0.0.1:8000. Состояния `budget_exhausted`, `failed`,
устаревшие потоки и отсутствие heartbeat видны в верхней строке панели.
Успешное пустое окно считается проверенным; ошибка или усечение — нет.
Полнота интервалов и свежесть последнего окна показываются отдельно.

## Лимиты и восстановление

По умолчанию: 6 HTTP-запросов Bitquery в минуту, резерв 10 points на каждый
GraphQL-запрос, 100 points на запуск, 200 на UTC-сутки, минимум 20 points
остаётся на счёте. Повторы тоже расходуют лимит. Usage API проверяется при
старте и раз в пять циклов; его счётчики могут запаздывать.

Резервы сохраняются в SQLite до отправки запросов. Перезапуск не обнуляет
суточный резерв и накопленный резерв текущего billing period. Это консервативная
оценка: фактическая стоимость отдельных запросов может отличаться; локальный
лимит не является гарантией суммы счёта поставщика. Другие программы с этим
аккаунтом тоже могут расходовать квоту.

Настройки: `ARC_REQUESTS_PER_MINUTE`, `ARC_POINTS_PER_RUN`, `ARC_POINTS_PER_DAY`,
`ARC_POINTS_PER_REQUEST`, `ARC_POINTS_RESERVE`; пример — `.env.example`.
`ARC_TOKEN_EXPIRES_AT` задаёт известный срок токена. Если он неизвестен,
система так и показывает; конец billing period не используется вместо него.
Авторизация и GraphQL-ошибки явно останавливают основной сбор.

Сначала poll сохраняет свежие launches/trades, затем исправляет по одному
старому пропуску каждого потока за цикл. Незавершённое окно не получает coverage.
Временные ошибки Bitquery повторяются с ограниченным backoff. ОС освобождает
writer lock после аварии; следующий запуск отмечает брошенный процесс в журнале.
Контроллер не поддерживает управляемый сбор в PostgreSQL: эта эксплуатационная
схема рассчитана на локальную SQLite-базу.

```powershell
.\.venv\Scripts\python.exe -m arc_monitor quota
.\.venv\Scripts\python.exe -m arc_monitor cost --requests-per-hour 120
.\.venv\Scripts\python.exe -m arc_monitor probe-history --dates 2026-09-16T00:00:00Z 2026-09-21T00:00:00Z
.\.venv\Scripts\python.exe -m arc_monitor backfill --start 2026-09-21T00:00:00Z --end 2026-09-21T00:02:00Z
```

120 запросов/час — только сценарий двух потоков раз в минуту. Дробление,
ремонт пробелов и обогащение увеличивают расход. `cost` не вычисляет денежную цену
без данных о тарифе. `probe-history` проверяет наличие хотя бы одной строки;
пустой ответ не доказывает отсутствие событий или границу хранения.

## Автозапуск Windows

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/install_autostart.ps1
# Удалить только эту задачу:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/install_autostart.ps1 -Remove
```

Задача `ArcMonitor-Collector`: при входе текущего пользователя и ежедневно в 04:00
локального времени, скрытое окно, без повышения привилегий, без параллельных копий.
После неуспешного завершения — до трёх повторов через пять минут. Суточный предел
переживает повторы: они не открывают новый бюджет. Ежедневный запуск возобновляет
работу после смены UTC-дня. Требуется активная пользовательская сессия; выключенный
компьютер данные не собирает. Журналы: `reports/monitor/collector-YYYY-MM-DD.log`.

Trial-квота не обеспечивает непрерывный сбор сутки напролёт. При достижении
лимита процесс остановится с сохранённой причиной. Повышать бюджет без понимания
тарифа не нужно; для длительного покрытия нужен достаточный остаток/тариф.

## Дополнительные данные и проверка гипотезы

```powershell
.\.venv\Scripts\python.exe -m arc_monitor enrich --max-tokens 3 --max-wallets 10
.\.venv\Scripts\python.exe -m arc_monitor reconcile --limit 3
.\.venv\Scripts\python.exe -m arc_monitor cctp --start 2026-09-22T18:00:00Z --end 2026-09-22T18:02:00Z
.\.venv\Scripts\python.exe -m arc_monitor evaluate --out reports/evaluation-live
.\.venv\Scripts\python.exe -m arc_monitor notify
```

`poll` обогащает ограниченный набор раз в десять циклов, начиная с первого;
`--enrich-every 0` отключает его. `--cctp` добавляет реконсиляцию CCTP.
Срезы holders/liquidity и контрактные сведения собираются сейчас, а не задним
числом. Funding — первый **наблюдаемый** входящий ERC20 USDC в ограниченном окне
до покупки; это не доказательство первого пополнения или независимости человека.
История creator относится к запускам, наблюдаемым в этой базе.

Неполные holders не становятся полными, проверка interface/owner/proxy не заменяет
аудит безопасности. Источники и ограничения: [ENRICHMENT.md](ENRICHMENT.md),
[CCTP.md](CCTP.md), [HISTORY.md](HISTORY.md).

`evaluate` сравнивает фиксированные правила на временных train/test когортах;
незрелые и непокрытые окна цензурируются. Комиссии, проскальзывание, налоги и размер
позиции учитываются только как условная модель. Текущие наблюдения не доказывают
исполнимую доходность. См. [EVALUATION.md](EVALUATION.md).

Telegram по умолчанию не отправляет сообщения. `notify` — dry run; явные
`notify --send` или `poll --telegram` требуют `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`
и допустимый отчёт, связанный хешами с данными и настройками. До независимого
исследования и подтверждения исполнимости gate закрыт. В текущем протоколе
исполнимость остаётся неподтверждённой, поэтому готовых торговых сигналов нет.
Истёкшее окно доставки фиксируется, а неоднозначный сетевой результат не
пересылается автоматически: Telegram не предоставляет ключ идемпотентности.
