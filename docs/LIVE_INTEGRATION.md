# Проверка Bitquery с ключом — 22 сентября 2026

Проверено на Windows в локальном checkout `arc_monitor`, примерно 18:00–18:06 UTC.
Ключ прочитан из локального `.env` только внутри диагностических процессов.
Значение ключа не выводилось. CLI по-прежнему **не загружает `.env` автоматически**.
Код приложения и настройки запуска в этой проверке не менялись.

## Что подтверждено

- Авторизация и текущие GraphQL-запросы `Trading.Trades` и `EVM(network: arc).Events` работают.
- Контрольная выборка: 10 сделок при лимите 10 и 5 launch-событий; все прошли нормализацию.
  Усечённая выборка из 10 сделок не использовалась как доказательство покрытия.
- Два свежих интервала сохранены в существующую live-базу `data/arc.db`, вместе с raw-ответами.
- Повторный запрос первого интервала с `refresh=True` добавил **0 записей** для каждого потока.
- Официальный RPC `https://rpc.mainnet.arc.io` ответил chain ID `0x13b2` (5042).
- Для трёх реальных сделок получены receipts и `decimals()` на историческом блоке.
  Совпали время, адрес токена, направление покупки/продажи и кошелёк с отправителем.
  Для v2/v3 адрес пула присутствует в receipt; для v4 также найден отдельный Pool.Id в topics.

Сравнивались переводы к пулу / от пула, а не полное изменение баланса кошелька:
комиссии роутера и gas отдельно не включены. Системное зеркало USDC не складывалось с ERC-20.
Это выборочная сверка простых сделок, а не универсальный декодер swap-событий.

Дополнительный запрос с разбором чисел JSON как строк подтвердил: значения
`3110.6152` и `404.16748` уже округлены в ответе Bitquery. `Decimal` сохраняет полученное
значение, но не восстанавливает точные on-chain amounts. Поэтому нельзя считать
текущие поля эквивалентом исходных целочисленных сумм контракта.

Дедупликация по fingerprint прошла повторную загрузку. Не доказано, что она сохраняет
две разные, полностью одинаковые по выбранным полям swap-операции внутри одной транзакции.
Привязка каждой строки к конкретному RPC logIndex остаётся отдельной доработкой.

## История и квота

Проверены пятиминутные окна 12:00–12:05 UTC с лимитом **1 строка**:

| Дата | trades | launches |
|---|---|---|
| 2026-09-16 | Есть строка | Пустой успешный ответ |
| 2026-09-19 | Есть строка | Есть строка |
| 2026-09-21 | Есть строка | Есть строка |

Эти запросы подтверждают наличие отдельных записей. Они не определяют самую раннюю
доступную дату и не подтверждают полноту диапазона. Пустой ответ launches за 16 сентября
не позволяет отличить отсутствие событий в выбранном окне от ограничения доступной истории.
Историческое покрытие по этим пробам в базу не записывалось.

Usage API вернул `active`, план `Trial plan`, лимит 1000 points и 10 запросов в минуту.
Период в ответе: `2026-09-22T17:52:43Z` — `2026-10-22T23:59:59Z`;
это срок периода аккаунта, **не проверенный срок действия токена**.
Снимки 18:04:30 и 18:05:17 UTC оба показывают 40 points / 10 requests, хотя между ними
выполнены ещё два GraphQL-запроса. Счётчик не отразил эти запросы немедленно;
разницу нельзя объявлять нулевой стоимостью сбора.
В ответах GraphQL не было billing-заголовков или `extensions` с ценой запроса.

Два запроса собрали последний двухминутный интервал без дробления. Для такого режима
без перекрытия это арифметически 60 запросов/час и 1440/сутки. Это **не оценка points
или денег**, не замер стандартного `poll` и не готовая рекомендация для непрерывного сбора.
Стандартный polling повторяет десятиминутный lookback, а насыщенные окна дробятся;
его фактическое число запросов будет выше. Нужны измерение отложенного биллинга,
ограничитель частоты, контроль остатка points и проверка свежести/пропусков.
