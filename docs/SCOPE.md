# Покрытие исходного задания

| Пункт задания | Состояние | Граница реализации |
|---|---|---|
| 1. Четыре уровня наблюдения | Частично | Token, creator, scoped ecosystem; launchpad-фильтр, без полной cohort-панели |
| 2. Bitquery | Live-сбор и контроль расхода | `.env`, pace, run/day/account reserves, usage, history probes, gaps/freshness; стоимость в points — сценарий, не денежный счёт |
| 3. Независимый RPC | Частично | chain, uint calls, registry logs; не полноценный независимый swap indexer/Arcscan REST |
| 4. Launchpad discovery | Частично | 8 factory/strategy entries и indexed token; social/fees/старые версии не полностью |
| 5. Generic discovery | Частично | Первая подходящая сделка; не contract creation → ERC20 → Initialize |
| 6. Token metrics | Частично | Основные торговые/ценовые метрики, неизвестные поля null; supply только из входного среза |
| 7. Holders | Ограниченный текущий автосбор | limit+1, raw provenance, ротация токенов; полный исторический срез не заявляется |
| 8. Creator history | Частично | Другие наблюдаемые launches, зрелые/цензурированные survival 24h; не полный creator P&L |
| 9. Wash detector | Частично | Round trips/same transaction, concentration; не все перечисленные признаки |
| 10. Wallet clusters | Ограниченный funding-автосбор | Первый наблюдаемый ERC20 USDC transfer в заданном окне до покупки; не first-ever, не доказательство независимых людей |
| 11. Buyer velocity | Реализовано | Новые wallets 5m, предыдущие 5m; Runner использует группы-proxy |
| 12. Retention | Частично | Возврат первых покупателей через 30m; не все когорты и горизонты |
| 13. Survival / runner labels | Реализовано формально | 1/6/24/72h и будущие цены; правила не откалиброваны на рынке |
| 14. Liquidity retention | Расчёт и текущий автосбор | Gecko известного пула, USD при USDC peg, время получения; исторический backfill не заявляется |
| 15. Chain/CCTP regime | Ограниченная CCTP V2-реконсиляция | Canonical receipts, message/protocol/USDC transfers, gross/net/fee evidence; неоднозначные окна остаются непокрытыми |
| 16. USDC decimals | Реализовано | 18/6 conversions, одна величина вместо суммирования representations |
| 17. Внешние cross-check | Частично | Текущий известный Gecko-пул; DEXScreener отсутствует |
| 18–19. Архитектура/таблицы | Реализована основа | SQLite default, PostgreSQL SQLAlchemy path; без migrations/Parquet |
| 20. Stages / экономия API | Частично | Темп, постоянные резервы, квота, ротация enrichment, приоритет свежих окон; нет адаптивных WebSocket-подписок |
| 21. Два score | Реализовано | Раздельные некалиброванные эвристики; null Risk при неполных основных свидетельствах |
| 22. Alerts | Telegram-адаптер с закрытым research gate | Dry run по умолчанию; fingerprint данных/правила, дедупликация, учёт неопределённой доставки; фактических отправок нет |
| 23. Backtest | Purged hold-out механизм и live-отчёт | Сравнение правил и ablations, false alerts, условные комиссии/slippage/capacity; текущий результат insufficient_data |
| 24. Три стадии проекта | Первая инженерная поставка | Нет утверждения, что рыночная гипотеза уже проверена |

## Что проверено и что ещё ограничивает результат

Эксплуатация и команды: [OPERATIONS.md](OPERATIONS.md). Текущий отчёт:
[DELIVERY_2026-09-22.md](DELIVERY_2026-09-22.md). Первичная live-интеграция:
[LIVE_INTEGRATION.md](LIVE_INTEGRATION.md).

Инженерные механизмы этапов 2–5 добавлены. Это не означает, что исследовательская
гипотеза подтверждена или что ключ с Trial-квотой обеспечивает непрерывный сбор.

- История проверяется отдельно для launches/trades/CCTP. Наличие строк в коротком
  окне не доказывает всю доступную глубину; пробелы базы остаются видимыми.
- Holders/liquidity/контрактные сведения сохраняются со временем получения.
  Полные исторические holders, аудит налогов/продажи/LP и полный creator P&L
  остаются за пределами текущих адаптеров. Неизвестные поля не заполняются нулями.
- На текущей live-базе не хватает непрерывных feature/label окон для независимых
  train/test когорт. До их накопления оценки precision и доходности не публикуются.
- Windows-задача запускает сбор при входе пользователя и ежедневно, восстанавливает
  ограниченные сбои. Квота имеет приоритет: остановка по бюджету ожидаема и видима.
- Telegram не отправляет сообщения до допустимого исследования; текущий gate
  закрыт. WebSocket не добавлялся: на этом этапе используется ограниченный polling.
